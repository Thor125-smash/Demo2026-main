Ниже представлены команды для проверки каждого пункта оценочной ведомости с подробными пояснениями — что именно проверяется, на каком устройстве и как интерпретировать результат.

---

## **А1 – Сеть и маршрутизация**

### **А1-1 – Имена узлов соответствуют заданию**
**Где выполнять:** На всех устройствах (HQ-RTR, HQ-SRV, HQ-CLI, BR-RTR, BR-SRV, ISP, ISP2)  
**Команда:**
```bash
hostname
```
**Пояснение:** Команда отображает текущее имя устройства. Оно должно точно совпадать с указанным в задании (например, HQ-RTR, BR-SRV и т.д.). Имена важны для идентификации устройств в сети и в документации.

---

### **А1-2 – Расчёт IP адресов локальных сетей офисов HQ и BR соответствует заданию**
**Где выполнять:** HQ-RTR, BR-RTR  
**Команда:**
```bash
ip a                     # Linux
show running-config interface  # Cisco
```
**Пояснение:** Проверяем IP-адреса на интерфейсах, которые подключены к локальным сетям. Они должны попадать в подсети, рассчитанные по заданию (например, 192.168.1.0/24, 10.0.0.0/24 и т.д.). Несоответствие нарушит маршрутизацию.

---

### **А1-3 – Подняты все необходимые sub-интерфейсы на HQ-RTR**
**Где выполнять:** HQ-RTR  
**Команда:**
```bash
show vlan brief
show interfaces trunk
show running-config interface
```
**Пояснение:** Sub-интерфейсы (например, G0/0.10, G0/0.20) создаются для маршрутизации между VLAN. Проверяем, что все нужные VLAN настроены и привязаны к физическому интерфейсу.

---

### **А1-4 – PAT на HQ**
**Где выполнять:** HQ-RTR  
**Команда:**
```bash
show ip nat translations
show running-config | include nat
```
**Пояснение:** PAT (Port Address Translation) позволяет устройствам из локальной сети выходить в Интернет, используя один внешний IP. Должны быть правила `ip nat inside source list ... interface ... overload`.

---

### **А1-5 – PAT на BR**
**Где выполнять:** BR-RTR  
**Команда:**
```bash
show ip nat translations
show running-config | include nat
```
**Пояснение:** Аналогично предыдущему пункту, но для офиса Branch. Проверяем наличие правил NAT.

---

### **А1-6 – Туннельное соединение между офисами**
**Где выполнять:** HQ-RTR, BR-RTR  
**Команда:**
```bash
show interfaces tunnel
show running-config interface tunnel
ping <туннельный_адрес_удалённой_стороны>
```
**Пояснение:** Туннель (например, GRE) создаёт виртуальный канал между офисами через Интернет. Проверяем, что интерфейс tunnel поднят и есть ICMP-доступность удалённой стороны.

---

### **А1-7 – OSPF только по туннелю**
**Где выполнять:** HQ-RTR, BR-RTR  
**Команда:**
```bash
show ip ospf interface
show running-config | section router ospf
```
**Пояснение:** OSPF должно работать только через туннельный интерфейс, чтобы не анонсировать внутренние сети наружу. Проверяем, что в настройках OSPF нет команд `network`, охватывающих физические интерфейсы.

---

### **А1-8 – Пассивные интерфейсы на HQ-RTR**
**Где выполнять:** HQ-RTR  
**Команда:**
```bash
show running-config | include passive-interface
```
**Пояснение:** Пассивные интерфейсы не отправляют OSPF-приветствия, но участвуют в маршрутизации. Обычно это интерфейсы, обращённые к клиентам.

---

### **А1-9 – Аутентификация OSPF**
**Где выполнять:** HQ-RTR, BR-RTR  
**Команда:**
```bash
show running-config | section router ospf
show ip ospf interface
```
**Пояснение:** Должна быть настроена аутентификация (обычно MD5) для защиты маршрутной информации. Проверяем наличие команд `ip ospf authentication message-digest` и ключей.

---

### **А1-10 – Связность между офисами и Интернетом**
**Где выполнять:** HQ-CLI, BR-SRV  
**Команда:**
```bash
ping 8.8.8.8
ping <адрес_сервера_в_другом_офисе>
```
**Пояснение:** Проверяем доступ в Интернет и связность между офисами. Если пинг идёт, значит маршрутизация и NAT настроены правильно.

---

### **А1-11 – DHCP работает**
**Где выполнять:** HQ-RTR, HQ-CLI  
**Команда:**
```bash
# На маршрутизаторе
show ip dhcp binding
show running-config | section dhcp

# На клиенте
ip a
```
**Пояснение:** DHCP должен выдавать клиентам IP-адреса. Проверяем, что пул адресов настроен и клиент получил адрес.

---

### **А1-12 – DNS работает на HQ-SRV**
**Где выполнять:** HQ-SRV, HQ-CLI  
**Команда:**
```bash
# На сервере
systemctl status named
dig @localhost <домен>

# С клиента
nslookup hq-srv.au-team.irpo <HQ-SRV_IP>
```
**Пояснение:** DNS-сервер должен отвечать на запросы. Проверяем статус службы и резолвинг имён.

---

### **А1-13 – Разрешается запись прямых зон на HQ-SRV**
**Где выполнять:** HQ-SRV  
**Команда:**
```bash
ls -la /var/named/
nsupdate -l
```
**Пояснение:** Должна быть возможность динамического обновления записей в прямых зонах (например, A-записи). Проверяем права на каталог зон и пробуем добавить запись через nsupdate.

---

### **А1-14 – Разрешается запись обратных зон**
**Где выполнять:** HQ-SRV  
**Команда:**
```bash
ls -la /var/named/
nsupdate -l
```
**Пояснение:** Аналогично, но для обратных зон (PTR-записи). Проверяем наличие и права на файлы обратных зон.

---

### **А1-15 – Узлы ISP имеют связь с Интернетом**
**Где выполнять:** ISP, ISP2  
**Команда:**
```bash
ping 8.8.8.8
```
**Пояснение:** Проверяем, что провайдерские маршрутизаторы имеют выход в глобальную сеть.

## **А2 – Сервисы и администрирование**

### **А2-1 – Пользователи sshuser на HQ-SRV и BR-SRV с sudo без пароля**
**Где выполнять:** HQ-SRV, BR-SRV  
**Команда:**
```bash
sudo -l -U sshuser
```
**Пояснение:** Проверяем, что пользователь sshuser может выполнять любые команды через sudo без запроса пароля (должно быть `NOPASSWD: ALL`).

---

### **А2-2 – Пользователи net_admin на маршрутизаторах с sudo без пароля**
**Где выполнять:** HQ-RTR, BR-RTR (если Linux, если Cisco – см. ниже)  
**Команда (Linux):**
```bash
sudo -l -U net_admin
```
**Команда (Cisco):**
```bash
show running-config | include username
```
**Пояснение:** На Cisco проверяем наличие пользователя с привилегированным уровнем, на Linux – права sudo.

---

### **А2-3 – SSH работает на HQ-SRV, BR-SRV**
**Где выполнять:** HQ-SRV, BR-SRV  
**Команда:**
```bash
systemctl status sshd
ss -tlnp | grep 22
```
**Пояснение:** SSH-сервер должен быть активен и слушать порт 22. Проверяем статус службы и открытый порт.

---

### **А2-4 – Настройка NTP**
**Где выполнять:** Все серверы и маршрутизаторы  
**Команда (Linux):**
```bash
timedatectl status
chronyc sources -v
```
**Команда (Cisco):**
```bash
show ntp associations
```
**Пояснение:** Время должно быть синхронизировано. Проверяем источники времени и статус синхронизации.

---

### **А2-5 – Развёртывание домена на BR-SRV**
**Где выполнять:** BR-SRV  
**Команда:**
```bash
realm list
hostname
```
**Пояснение:** Сервер должен быть контроллером домена `au-team.irpo`. Проверяем членство в домене и имя хоста.

---

### **А2-6 – HQ-CLI в домене, пользователи созданы**
**Где выполнять:** HQ-CLI  
**Команда:**
```bash
realm list
getent passwd <пользователь_из_домена>
```
**Пояснение:** Клиент должен быть введён в домен, и пользователи из домена должны быть доступны для аутентификации.

---

### **А2-7 – Разрешено выполнение команд для пользователей на HQ-CLI**
**Где выполнять:** HQ-CLI  
**Команда:**
```bash
sudo -l -U <пользователь>
```
**Пояснение:** Проверяем, что доменные пользователи имеют права на выполнение определённых команд (например, через sudoers или групповые политики).

---

### **А2-8 – Docker работает**
**Где выполнять:** HQ-SRV, BR-SRV  
**Команда:**
```bash
systemctl status docker
docker ps
```
**Пояснение:** Docker-демон должен быть запущен, и контейнеры должны работать без ошибок.

---

### **А2-9 – Файл инвентаря Ansible**
**Где выполнять:** Управляющий хост с Ansible  
**Команда:**
```bash
cat inventory.ini
```
**Пояснение:** В инвентаре должны быть перечислены все управляемые хосты с правильными группами и параметрами доступа.

---

### **А2-10 – Машины отвечают без предупреждений**
**Где выполнять:** Управляющий хост  
**Команда:**
```bash
ansible all -m ping -i inventory.ini
```
**Пояснение:** Проверяем доступность всех хостов через Ansible. Должен быть `SUCCESS` для каждого.

---

### **А2-11 – podg на ansible ping**
**Где выполнять:** Управляющий хост  
**Команда:**
```bash
ansible podg -m ping -i inventory.ini
```
**Пояснение:** Проверяем доступность хостов из группы `podg` (например, серверы с подсистемой).

---

### **А2-12 – База данных для web приложения**
**Где выполнять:** Сервер БД  
**Команда:**
```bash
mysql -u root -p -e "SHOW DATABASES;"
mysql -u root -p -e "USE <db_name>; SHOW TABLES;"
```
**Пояснение:** Проверяем наличие базы данных и загруженного дампа (таблицы должны быть созданы).

---

### **А2-13 – Web приложение доступно**
**Где выполнять:** Любой хост с доступом к приложению  
**Команда:**
```bash
curl -u user:password http://<IP_приложения>/
```
**Пояснение:** Приложение должно отвечать по HTTP с аутентификацией. Проверяем статус-код и содержимое ответа.

---

### **А2-14 – Веб и контейнер доступны по внешнему адресу маршрутизатора**
**Где выполнять:** Внешний хост (например, ISP)  
**Команда:**
```bash
curl http://<внешний_IP_маршрутизатора>:<порт>/
```
**Пояснение:** Проверяем, что проброс портов настроен, и приложения доступны извне.

---

### **А2-15 – Проксирование имён на ISP**
**Где выполнять:** ISP  
**Команда:**
```bash
cat /etc/nginx/sites-available/   # Проверка конфигурации
curl -H "Host: docker.au-team.irpo" http://<IP_ISP>/
```
**Пояснение:** На ISP должен быть настроен веб-сервер (nginx/Apache) для проксирования запросов по именам `docker.au-team.irpo` и `web.au-team.irpo` к внутренним ресурсам.

---

### **А2-16 – Дисковый массив и авто-монтирование**
**Где выполнять:** Сервер с массивом  
**Команда:**
```bash
df -h
cat /etc/fstab
mount -a
```
**Пояснение:** Проверяем, что RAID или LVM массив смонтирован и автоматически монтируется при загрузке (запись в fstab).

---

### **А2-17 – Автоматическое монтирование общего ресурса на HQ-CLI**
**Где выполнять:** HQ-CLI  
**Команда:**
```bash
df -h | grep //...
cat /etc/fstab
```
**Пояснение:** Проверяем, что сетевая папка (CIFS/NFS) примонтирована автоматически. В fstab должна быть соответствующая запись.
